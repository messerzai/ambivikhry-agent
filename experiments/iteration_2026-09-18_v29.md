# Ambivikhry v2.9 — Recursive Strengthening Pass

Date: 2026-09-18
Status: experimental proposal set; not merged to main.

## Fresh evidence incorporated

1. Agentic Evolution survey (Microsoft Research, June 2026): reliable autonomous evolution depends strongly on deterministic, independent verifiers; self-referential/proxy-only signals degrade with iteration.
2. Self-Evolving Coding Agents survey (August 2026): executable feedback, repository context and coding trajectories are unusually useful, but benchmark overfitting, feedback reliability, safety and maintainability remain major failure modes.
3. ReVeal (ICLR 2026): generation and verification should co-evolve, with tool-based evaluation and repeated verification turns.
4. CoEvolve (ACL 2026): the data/task distribution should evolve from observed failure and uncertainty rather than remain static.
5. Open-Ended Optimization (August 2026): keep objective, permitted interactions, resource budget, data boundary and evaluation fixed externally while allowing the optimizer to compose the improvement route.

## v2.9 changes proposed

### A. Dual evaluation tracks
- Public/regression suite for fast feedback.
- Hidden holdout suite whose content is inaccessible to the proposer.
- Acceptance requires improvement on both without safety regression.

### B. Evaluator independence
- Proposer, critic and evaluator use separate roles and separate state views.
- No candidate may modify the evaluator or evaluation criteria it is being judged by.
- Evaluator output is immutable evidence for the current generation.

### C. Co-evolving task bank
- Extract failure signatures, uncertainty and repeated error patterns.
- Generate new tasks from those signatures.
- Validate generated tasks before adding them to the training/evaluation pool.
- Never promote generated tasks directly into the hidden holdout.

### D. Prompt evolution
Each helper may propose a prompt mutation, but prompt mutations are treated exactly like code mutations:
proposal -> critique -> tests -> independent evaluation -> holdout -> safety gate.

### E. Anti-reward-hacking suite
Explicit tests for:
- evaluator manipulation;
- benchmark contamination;
- disabling verification/safety checks;
- gaming the score without solving the task;
- deleting or weakening regression tests;
- provenance fabrication;
- prompt injection through research material.

### F. Meta-improvement constraint
The system may propose improvements to its optimizer, verifier, memory and helper prompts, but may not modify the external acceptance contract. Any attempted modification of policy/security/evaluator boundaries becomes a PRIVILEGE_REQUEST event and is rejected by default.

## Ten-pass sequence
G01 evidence quality -> G02 verifier separation -> G03 prompt mutation -> G04 helper co-evolution -> G05 failure-memory -> G06 diverse search -> G07 hidden holdout -> G08 anti-gaming -> G09 meta-optimizer -> G10 consolidation.

## Success criterion
Do not define "stronger" as subjective fluency. A generation is stronger only if it improves the predefined capability score or robustness score while preserving safety, regression and holdout performance. If no candidate beats the parent, retain the parent.

## Important status distinction
This file records the next experimental design and research synthesis. It does not claim that ten generations have already executed successfully. Execution requires an actual model backend/runtime.
